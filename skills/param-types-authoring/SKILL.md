# Как описать скилл типов параметров плагина

Научись сам (или научи агента) создавать скилл, который документирует
**кастомные типы параметров конкретного плагина** — те, что плагин регистрирует
через API `ParamsController`, а не встроенные типы контроллера.

Скилл — **про типы и только**: что писать в JSON, что попадёт в `Trie`, каким
геттером читается, условия ошибки и побочные эффекты. Общие механизмы
ParamsController (регистрация параметров, синтаксис тегов, чтение значений кодом,
семантика ошибок чтения) в него **не входят** — они живут в отдельном общем скилле.

## Когда применять / не применять

**Применять**, когда:
- просят задокументировать / описать типы параметров плагина;
- нужно создать скилл для типов, которые плагин регистрирует сам
  (`ParamsController_RegSimpleType` / `ParamsController_ParamType_Register`);
- в плагине появился новый кастомный тип, и существующий скилл надо дополнить.

**Не применять**, когда:
- нужно описать **встроенные** типы ParamsController (`Boolean`, `Integer`,
  `RGB`, `Model`, …) — для них уже есть скилл `param-types`;
- нужно описать **общие механизмы** ParamsController (теги, чтение, ошибки) — не сюда;
- нужно писать/править код плагина.

## Встроенные vs кастомные

Встроенные типы регистрирует сам контроллер — они одинаковы во всех проектах.
Кастомные типы плагин регистрирует у себя, обычно в форварде
`public ParamsController_OnRegisterTypes()`:

```pawn
public ParamsController_OnRegisterTypes() {
    ParamsController_RegSimpleType("MyType", "@OnReadMyType");
}
```

В скилл плагина попадают **только кастомные типы**. Встроенные — не дублируем,
а ссылаемся на скилл `param-types`.

Помимо регистрации типов плагины часто объявляют **собственные функции-хелперы
чтения** этих типов — по образцу стандартных `PCGet_*` / `PCSingle_*` (иногда со
своим префиксом). Их тоже документируй: потребителю важно знать, *чем* читать
значение, а не только *как* его писать в конфиг.

> Типы, которые приходят из **другой зависимости** (транзитивно), — не ваши:
> у каждого плагина/библиотеки свой скилл. Документируйте только то, что
> регистрирует сам целевой плагин.

## Результат работы

Составной скилл той же формы, что и `param-types`:

```
<plugin-param-types>/
├── SKILL.md              # индекс: таблица типов + список групповых файлов
└── references/
    ├── <type-1>.md       # по файлу на каждый кастомный тип
    ├── <type-2>.md
    ├── _<group-1>.md     # (опц.) общий блок для группы типов
    └── _<group-2>.md
```

Индекс держи **лёгким**: таблица типов + перечень групповых файлов. Никаких
общих правил, ошибок чтения и чтения кодом — им место в общем скилле.

Групповой файл `references/_<группа>.md` заводи **только** когда один и тот же
текст нужен нескольким типам и отличается лишь именем/параметром типа (например:
«путь и проверка существования» для ресурсных, «лимит длины» для строковых,
«разбор числа» для числовых). Имена групповых файлов не фиксированы — называй по
группе/аспекту; в файлах типов ссылайся на них вместо копипасты.

Плюс запись в `skills:` манифеста плагина (`amxbuild.yml`).

Шаблоны:
- `references/skill-index-template.md` — заготовка `SKILL.md`;
- `references/type-reference-template.md` — заготовка `references/<тип>.md`;
- `references/finding-registrations.md` — как найти регистрации и хелперы в коде.

## Процедура

1. **Найти все регистрации типов** в целевом плагине — см.
   `references/finding-registrations.md`. Выпиши список имён типов и функций
   их колбеков.
2. **Прочитать каждый колбек** и выписать его контракт (см. «Что выписать»).
   Колбек может лежать в другом файле — ищи по имени из вызова регистрации.
   Там же найди функции-хелперы плагина для чтения этих типов.
3. **Написать `references/<тип>.md`** на каждый тип по
   `references/type-reference-template.md`.
4. **Собрать `SKILL.md`** по `references/skill-index-template.md`: таблица типов
   со ссылками на файлы. Дублируемые для нескольких типов блоки вынеси в
   `references/_<группа>.md` и перечисли их в индексе.
5. **Прописать скилл в манифесте** плагина (см. «Манифест»).
6. **Проверить** (см. «Проверка»).

## Что выписать для каждого типа

Контракт типа — это то, что нужно знать при настройке конфига и чтении значения
кодом. Минимум:

1. **Имя типа** — точная строка, как в вызове регистрации.
2. **Теги** — поддерживает ли `Тип:тег`; какие значения тега и что они меняют
   (колбек получает тег четвёртым аргументом); что при пустом/неизвестном теге.
3. **Допустимый JSON** — какие типы значений принимаются (`json_get_type`,
   `json_is_array`/`json_is_object`/`json_is_string`), какие форматы строк,
   какие поля объекта.
4. **Результат в Trie** — что и как пишется (cell / string / array).
5. **Условия ошибки** — какие входы заставляют колбек вернуть `false`.
6. **Мягкие преобразования** — что молча превращается в `0`/пусто **без** ошибки
   (частый источник «параметр стал нулём»).
7. **Побочные эффекты** — прекеш, проверка существования файла, загрузка модулей.
8. **Ограничения** — длины, диапазоны, клампы, обрезка.
9. **Чтение кодом** — функция/хелпер, которым значение читается: **собственный
   у плагина**, если объявлен, и/или стандартный (`PCGet_*`, `PCSingle_*`). Если
   своих хелперов нет — укажи подходящий стандартный по формату значения (для
   типов с тегом — с учётом тега). Конкретный геттер — в файле типа (раздел
   «Что получится в Trie»), не в индекс и не в групповой файл.

Если по колбеку что-то нельзя понять однозначно — так и напиши («не документировано /
поведение зависит от …»), но **не выдумывай** форматы.

## Манифест

Добавь запись в `skills:` манифеста плагина:

```yaml
skills:
  - dir: skills/<plugin-param-types>
    name: <Отображаемое имя>
    description: >-
      Типы параметров плагина <Название>: допустимые JSON-значения, что попадает
      в Trie, теги, условия ошибки, чтение значений кодом (хелперы).
      Покрывает <перечислить типы>.
```

`description` пиши так, чтобы по нему агент понял, когда скилл нужен, и
перечисли в нём имена типов.

## Проверка

```bash
# манифест валиден, скилл объявлен корректно
amxb validate
```

Через MCP-инструменты:
- `validate_manifest` — 0 errors/warnings;
- `get_agent_skills` / `list_agent_skills` — скилл виден и отдаёт `SKILL.md`
  вместе со всеми `references/*`.

Перед завершением сверь: **каждый** кастомный тип из кода есть в таблице
`SKILL.md` и имеет свой файл в `references/`, и наоборот — в скилле нет типов,
которых нет в коде.

## Анти-паттерны

- Дублировать встроенные типы вместо ссылки на скилл `param-types`.
- Тащить общие механизмы ParamsController (теги, чтение, семантику ошибок) —
  им место в общем скилле.
- Описывать типы чужих/транзитивных зависимостей как свои.
- Придумывать форматы значений «по аналогии» вместо чтения колбека.
- Пропускать условия ошибки и мягкие преобразования.
- Описывать только сторону настройки и забывать чтение кодом.
- Считать, что кроме стандартных `PCGet_*` / `PCSingle_*` хелперов нет, и не
  искать собственные функции чтения плагина.
- Дублировать общий для нескольких типов блок в каждом файле вместо
  `references/_<группа>.md`.
- Заводить `references/_<группа>.md` как «сборную солянку» из разных тем, а не
  под один реально дублируемый блок.
- Сваливать все типы в один `SKILL.md` без `references/` — теряется смысл
  подгрузки по требованию.
- Забыть `skills:` в манифесте — скилл не попадёт в MCP/serve.
